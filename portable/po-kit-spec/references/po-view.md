# PO view (how the exported document treats what is not known)
The spec files keep canonical English labels and inline source tags (Observed, Inferred from API, PO proposal, Unverified) because the lint and agents need them. The documents a Product Owner reads never show those tags. `scripts/po_transform.py` converts the spec at export time, for both the SRS (`build_srs.py`) and the web reader (`build_reader.py`):

1. **Status as a column.** Business rules and Acceptance criteria become tables `ID | Content | Status`. Status comes from the tag: Observed = seen on the app, Inferred from API = derived from calls, PO proposal = proposed, Unverified = to confirm. No tag in the sentence.
2. **TBD table.** "Open questions & assumptions" is exported as "To confirm" (vi: "Cần xác nhận"). Each row gets an id `TBD-<feature>.<n>`, the owner, priority, the verification result, and an empty "Due" column for the PO to fill. A one-line completeness sentence precedes it: rules observed or inferred out of all rules, TBD count, how many were checked on the app.
3. **Language.** Answer prefixes and leftover tags are shown in the document language. In running text "Unverified" becomes plain words ("chưa xác nhận").
4. **Document-level sections** from `config.json`: `assumptions`, `dependencies` (IEEE 830 section 2.5), `revisions` (change history on the cover page). `po_mode: false` returns the old tagged export.
5. **Format.** The frame follows ISO/IEC/IEEE 29148 at the table-of-contents level (introduction, overall description, specific requirements, appendices); each feature keeps the 16-block template. A company template replaces the frame via `workflow `export-custom``.
6. **PO decisions.** `PO decided <date>` is a fourth status ("PO đã chốt"); it counts as confirmed in the completeness sentence and as an answer in the TBD table. It is written only by `po_sheet_import.py` or from a PO's own words, never by an agent's guess.
7. **Rule for writers.** An unknown is never written as fact: tag it, and add an Open questions row with an owner. A TBD closes only when its answer starts with Verified, Partly verified or Cannot verify and the feature text is updated; then bump `version` and add a `revisions` row.
7. **Test cases go to a per-module appendix** (Appendix E) in the exported documents, because most readers of an SRS are not QA. Each use case keeps its acceptance criteria; the appendix lists the test cases per use case with the same ids. `tests_to_appendix=False` in `po_transform.transform` keeps them inside each use case (use it when QA is the main reader).
8. **Acceptance criteria language** follows the document language (vi: Cho / Khi / Thì; en: Given / When / Then). The spec files keep Given / When / Then for the lint.
9. **Due date** is left empty on every TBD for the PO to fill; the kit never invents a deadline.
